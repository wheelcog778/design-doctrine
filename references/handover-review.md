# 接手外来交付包 / 评审别人的评审

触发：别人（另一个 agent、外包、另一台机）交来一个 zip + 一份交接单；或把一份「我给这个包打了分、
提了三条建议」的评审丢给你，要你决定收不收、修什么。

一句话：**交接单是对方的自证。复核的活是「验声称」，不是「跑命令」。**

## 1 先做环境一致性，不是验收

0. 解压到**空目录且平铺**。交接单里的路径通常写 `pkg-a/`、`pkg-b/` 同级；解到各自子目录后
   每条命令都报 `can't open file`，看起来像包坏了，其实是路径没对齐。
1. 逐条跑交接单列的命令，**记退出码**。全过只说明「环境与对方一致」，不说明任何修复生效。
2. 再核件数、版本真源、跨文件重复、包内示例是否过同一个检查器——这是「包自洽」的最低线。

## 2 验声称：用包外自建的对抗输入

包内 selftest 只能证明它写过的预言没坏。一条新修的漏洞，必须用**包外**构造的输入复现旧行为。

每条声称至少三组输入：

- **绕过串**：原来能骗过检查器的那句话 / 那个参数（现在应当被抓住）；
- **合法对照**：同一条规则应当豁免的写法。收紧规则最常见的事故就是连合法用法一起杀，
  只测「漏洞被堵」会把这个事故放过去；
- **边界**：空、畸形、超长、缺行——不许崩，只许「无法判定」。
- **失败路径的报错要指对原因**：构造「全部样本都被拦掉」或「全部输入被判无效」的输入，看它说的原因
  对不对。把「N 条入场全部不可成交」报成「检查日期/代码是否对得上」，会把人送去查一个没坏的地方——
  按 M5 歧义算缺陷。报错必须带计数与真实原因，而不是复用一个通用的「没有可用数据」。
- **覆盖范围**：声称「A/B/C 三个入口都做了同一件事」时，逐个入口跑同一份数据、比同一个指标。
  功能常只接进一个入口（典型：只在 `ic` 接了样本过滤，`yearly` 仍走全样本），于是同一份数据出现两个数。
  文档说「都做了」而代码只接一处，按 M4 状态不一致算缺陷，不是文档笔误——修法是补代码或改口径表述，
  不能加一句「以 ic 为准」收场。

结论写成三行：`环境一致 / 声称成立 / 残留弱点`。残留弱点照样写进记录：按「改范围、改验收标准才问」
的规矩它不一定当场修，但必须点名，否则下一版会以为已经封死。

## 3 把对方的说法分四类（这一步决定「修什么」）

| 类 | 判据 | 处置 |
|---|---|---|
| 新缺陷 | 文档没写过、代码确实错、会改结论 | 本轮修 |
| 已写明边界 | 包内完整度表 / README / 脚本 docstring 已披露 | 不算缺陷；最多把披露搬进输出 |
| 设计使然 | 对方不认同口径（例：单人不得判通过） | 不改；要改就是改验收标准，问用户 |
| 建议有害 | 采纳后会让工具更差 | 拒绝并给反证 |

判「已写明边界」要去 grep 原文，不凭印象。把已披露的缺口重新发现一遍再计分，是评审最常见的注水方式；
反过来，只有「文档说不扱、输出也不提示」才升级成缺陷——静默才是缺陷，披露过的缺口只是边界。

## 4 评审别人的评审（对方给了评分 + 建议）

1. **自评不作验收**：作者给自己的分等同 `M1_src=solo`，最高只能当「作者认为」。先查它与包内完整度表
   是否同指标不同数：摘要一个、表里一个、包内原值一个——一个指标出现两个以上数，整份评分作废，
   不必逐条辩。
2. **逐条核代码，不看措辞**。「缺 CLI」「参数不生效」这类说法要落到函数签名、调用点、
   有没有 `__main__`；核完再判它是缺陷还是功能缺口。**行号别信**：对方引的行号可能来自旧快照，
   同一段代码过一轮补丁就漂十几二十行，按函数名现查的位置核，不按它给的行号核。
3. **任何「再加一条自动检查」的提案，先量误报率**：拿包内现有合规文档跑一遍，误报超过约 10% 不采纳
   （细则见 `self-check-tools.md` §4.6）。检查器的价值建立在零误报上，用户踩三次误报就会整体关掉它。
4. **「自动记账 / 自动累加」先问计量单位**：多重检验的 trials 按「改了哪个口径」计，不按运行次数计。
   重跑同一个预注册检验不算新试验；按运行次数记账会把调试重跑算成多重检验、逼人不敢重跑，
   而且复制一份数据目录就清零——是假合规，不是护栏。
5. **区分「它不是别的东西」**：拿回测引擎的尺子量证伪器，扣掉的分全是假的。包自己写了
   「我只回答 X、不回答 Y」，就核它 X 做得对不对，不按 Y 的完整度打分。
6. **把可执行的小修做成补丁文件**：最小改动的 unified diff + 一条能复现结论差异的输入，
   落到 `patches/`；口头结论下一轮就没人能应用。
7. **回执用一张「声称 / 实测 / 判定」表**，行是对方的每条升级项，列里放真实命令输出或数字；
   表后再分三段：它做对的、它退步的、要不要合。用户要的是决定，不是重新描述一遍他的包。

## 5 收口

- 用户说「只存档」时：**不并入仓、不改 skill、不重打包**；记下 sha256、字节数、件数，
  并在索引里写「已存档、未并入」——「已交付」与「已并入」是两种状态，混了下一轮就会拿错版本。
- 用户只点了其中一条（「我点头了」紧跟某个待批项）时：**只落那一条**，回执第一句写明「按点头只动了 X」，
  其余待定逐项列出。点头不是整轮授权；先扩范围再解释，等于把审批变成追认。
- 回执固定三行：**改了什么（各自版本号）/ 验了什么（命令 + 退出码）/ 还差什么（没动的文件与状态）**。
  「验了什么」只算解压到新目录后跑出来的结果，打包目录上的通过不算。
- 收新版本前先做**回归 grep**：拿你上一版新加的符号名（函数名、常量、新的退出码取值）在新包全树搜一遍。
  版本号更高不等于含你的修复——对方常从你改动之前的快照起分支，直接收等于把修复回退掉。
  搜不到就写进合并清单并注明「它比我们少这一项」，不按「它更新」放行。
- 真并入时按「分叉 ≠ 新旧」处理：先按函数比、再按对抗输入实测，最后才同步仓与技能目录；
  同义事实的合并与唯一落点见 `references/consolidation-pass.md`。
- 没跑过的验证写「未验证」，不许用「应该没问题」代替；没改的文件要明说没改。
