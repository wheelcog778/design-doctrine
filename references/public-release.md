# 对外分发：把内部方法/工具包脱敏成别人能用的版本

触发：内部包（教义、框架、工具、报告集）要外传、出售、发给别人用，而里面有真实项目、实测数据、个人说明；
或已有脱敏版、但带着行业味，别人在别的域用不上。

一句话主张：**名字可以改，证据必须删。** 留着实测数字比留着项目名更危险——数据不在包里，读者验不了，
等于教他引用不可验证的数；而且具体的样本数、观测数、区间组合本身就是最精确的指纹。

## 七步

### 1 先立账，不动手

grep 出全部标识面，逐条记「文件:行」：真名与化名别名 / 项目与产品名 / 内部目录与脚本名 / 兄弟 skill 名 /
数据源目录 / 绝对路径 / 样本与区间数字 / 统计量与净值 / 具体日期区间 / 个人关系（家人、朋友、客户）。
**数字要当标识物搜**，不能只搜名字。

### 2 三类处置，逐条落

| 处置 | 对象 | 做法 |
|---|---|---|
| **删** | 项目叙事、案例文件、个人偏好说明、指向内部路径的复算命令 | 整件不进包 |
| **抽象** | 实测数字、内部字段/路径名 | 换成结构性描述：「样本量一小符号就翻转」而不是「A 组 +1.2% / B 组 −1.8%」；路径换成通用字段名 |
| **抽件** | 案例文件里承担方法职能的部分（清单、判定表、读图法） | **先抽成独立通用文件，再删原文件** |

抽件顺序不能倒：SKILL 与路由表里的指针都指向案例文件，先删就会让整包引用悬空。抽出来的文件要自己站得住——
只留方法与顺序，不留被删项目的数字。

### 3 改署名与元数据

frontmatter 的 author、README 落款、许可证署名统一改。CC-BY-4.0 允许化名署名，用化名不违反许可。

### 4 降自评（最容易被跳过的一步）

删掉证据之后，**同一批结论的可信等级必须跟着降**：原来写「5 条有数字、5 条假设级」，脱敏后只能写
「全部假设级（L0–L1），可作经验引用、不可作结论引用」。同时在 README 开头写一节「删了什么 + 代价」，
说明为什么降级。不降级 = 拿读者看不见的证据给方法放贷，这是整套方法自己最反对的事。

### 5 脚本与示例数据同属泄漏面

self-test 的 fixture、示例报告、示例命令行里的真实样本数、真实区间、内部脚本名都要换掉。
检查脚本能跑通不等于包干净。

### 6 内链复验

包内每个 `references/x.md`、`scripts/x.py` 指针都要落到实际文件；被删文件名在正文每一处出现都要改，
包括路由表、执行件清单、README 的包内清单、版本节。

### 7 打包后解压再验

新目录解压 → 跑三件套：脚本 selftest、跨文件重复行扫描、泄漏 grep。**在打包目录上跑等于自证**，
目录里可能还有没进包的文件，验的却不是交付物。

解压后按**清单**再核五条，少一条都不算打包成功：

| # | 查什么 | 为什么单跑脚本不够 |
|---|---|---|
| 1 | 文件数与包内清单一致 | 少打一个文件，自检全绿也看不出来（实测：新增文件没进 zip，只被“列目录”抓到） |
| 2 | 必备件逐个点名存在（宪法/索引/新脚本） | 清单驱动，不凭印象 |
| 3 | selftest / version_lint / dup_scan 全过 | 验行为，不只验内容 |
| 4 | 泄漏 grep 命中为 0 | 新增文件最容易被漏扫 |
| 5 | 拿包内**示例**跑它的检查器 | 结论要符合它的身份：合成示例 → 不可引用；单人 M1 → 带风险交付 |

解压要用认 UTF-8 文件名标志（0x800）的工具：Python `zipfile.extractall` 或 7-Zip。MSYS/Info-ZIP 的 `unzip`
不认这个标志，中文文件名会解成乱码，随后 `sha256sum -c` 报 `No such file`——看着像包坏了，其实是解压器。
核一遍：`zipfile.ZipFile(z).infolist()` 里逐条看 `flag_bits & 0x800`。

## 通用化（脱敏之后，让别人在别的域也能用）

脱敏解决「不能带我的东西」，通用化解决「全是行业味，别人套不上」。两件事分开做，别混在一次改写里。

1. **先分两类词**：结构性（闸门、阶段、验收、状态卡、修复循环——跨域不变）与行业性（统计量名、净值、仓位、成本假设、
   行业专属的判定词）。只动后者，动前者等于把方法改坏。
2. **行业指标改成两列**：「通用问法 + 在你的域里对应什么」。不要一删了之——保留一个行业例子做锚点，
   同时给出别的域的例子（量化：IC 与稳健 t ／ 软件：AB 两组差 ／ 业务：命中率差）。只剩一个例子，
   读者会以为方法只能用于那一域；一个都不留，读者失去参照。
3. **分级与验收去名词**：L0–L5 的判据换成「独立观测数 / 是否过显著性 / 效果是否小于成本 / 是否做过样本外」，
   阈值一律写「本包不给，必须自标定」。通用版里出现任何具体刻度，就是给人抄错的机会。
4. **示例与模板换中性对象**：用一个会输出「该先做哪个」的中性工具做例子，字段写范围/模式/输出位置，
   不写本金/仓位/标的；验收判据写「阈值型指标（耗时、错误率、命中率、退出码）」，不写具体统计量。
5. **补一个走完全流程的合成示例**：通用版最缺的是「整条路长什么样」。写法：判据 → 数字表 → 判级（可以是判死）
   → 微动作 → 改造 → 交付状态卡 → 边界 → 重算命令骨架 → 可引用三条。
6. **合成示例必须自洽**：分项加总等于总数、百分比与分母对得上、分期之和等于合计。这份文档自己就要求算术可对账，
   示例算错等于当场自证方法不成立。
7. **示例要能过包内检查器**：结论文档写齐口径/数字表/判级/可信度/边界/重算命令，状态卡带 `<!-- gates: ... -->` 行；
   跑过 `--doc` 与 `--gates` 再叫「完整版」。检查器是包自己的闸门，示例过不了就是包自相矛盾。

## 两份并存时写清关系

内部执行版和对外版**不要宣称同步**：README 版本节写「由内部 vX 派生、删了什么」，内部版的改动清单
不搬过去。两份各自演化不叫漂移，叫两个产品；但必须写明关系，否则下一个人会拿错、或拿对外版当内部版的事实源。

## 源包已经干净时：派生分发件，别为了显得干活而改内容

立账 grep 对命名、项目、路径、数字全部 0 命中时，「再做一份脱敏版」不再是删内容，
而是**派生一个可交付的副本**。这时改正文等于制造假差异，下次对账没人分得清哪份是真的。

派生件的固定增量（缺一条就不算分发件）：

1. **分发声明**：写明由哪个版本派生、谁是唯一事实源、本包不单独修订、源升级后按同版本重出。
2. **文件数变化三处同步**：README 包内清单的树、正文里的结构计数（「全包 N 个文件」）、以及复述它的其它文档
   （如那份一页纸摘要）。加了交付件却只改一处，就是自己犯了「标题写 N、实际 N+2」。
3. **交付清单 + `SHA256SUMS.txt`**：清单逐文件给字节与哈希；覆盖不到自身与校验和文件时，行里写明「本文件 / 见包内」。
4. **版本号跟源走、不单独演进**：给派生件升大版本，读者会以为它比源新。
5. **复验在解压件上做**，并加核一条「示例跑包内检查器得到的结论符合它的身份」。

派生件与源包内容等价是**正确结果**，不是偷懒；写成「本次删除了 X」才是撒谎。

## 坑

- **只改名不改数字**——最常见的假脱敏。
- **删了案例没抽方法件**——路由表、执行件清单、正文引用三处同时悬空。
- **脱敏后自评照抄**——比泄漏更隐蔽，等于伪造可信度。
- **在 staging 目录验证**——验的是工作区，不是交付物。
- **复制整棵目录后整篇重写某文件**：工具会把「存在但本任务没读过」的副本拒写；先删副本再写，或先读它。
- **把出处声明也删了**：留着「归纳自 N 个真实项目（已脱敏）」是诚实的，删掉的是可识别内容，不是出处。
- **用 README 一句话给检查器开豁免**（「跑不过是因为它是流程卡，不是缺陷」）：这是把验证责任从工具收回作者。
  改法是让检查器对任何文档同判，README 只复述结论——流程卡跑出来就该是「不可引用」，那不是故障，也不是例外。
- **同一指标在正文与示例里各一个数**（正文写 A→B、示例写 C→D，模板基线又是第三个数）：改版和拼包时最常漏。
  打包前 grep 该指标的所有出现处（正文、示例、模板、脚本 fixture），统一成一个值；合成示例里的量一律标「未验证」。
- **示例照抄模板的表头**：跨文件整行重复会被 `doc_dup_scan.py` 判失败；示例里改成「骨架见 `templates.md` §X，这次填的是……」
  再列内容，不要复制表头。
- **结论文档漏「可信度速查」**：`--doc` 会把缺项数算进必需项，直接判「仅方法演练，不可引用」。
- **删干净了行业词、却留着「已验证域 = 某行业」的声明**：通用版据此自相矛盾。改成「标定域 + 不外推」，别假装跨域验证过。
- **三份并存（内部版 / 脱敏版 / 通用版）不指定主源**：下次改任何一份都不知道以哪为准。写明谁派生自谁、哪份是唯一事实源。
- **阈值全空、只写「自己标定」等于没给**：读者拿到的是一副骨架，最贵的部分留白。要么给出标定程序（基线 → MDE ≈ 2.8σ/√N → 经济底线 → 取大者），要么明说「本包不覆盖这一层」，别用四个字假装覆盖了。
- **想用 skill_manage 同步 skill 根目录的 README**：它只能写 `references/`、`scripts/`、`templates/`、`assets/`；
  README/版本号这类根目录文件要用直接文件工具改。改不动就至少在此处记一行“README 停在哪版”，别让它静默落后。

## 交付前自问

1. 每个数字都能在包里复算吗？不能 → 它就不该留在包里。
2. 删了之后的自评等级，和我写进 README 的等级一致吗？
3. 包内还有没有指向包外的路径、脚本名、项目名？
4. 这个包从今天起是独立产品了吗？版本号与内部版分开了吗？
5. 示例里的每个数都自洽吗？包内检查器（`--doc` / `--gates` / 重复行扫描）在解压件上真的过了吗？
