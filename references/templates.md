# 模板包

按产物出现的先后：规划 → P1 分工 → P2 口径 → P3 初步验收 → P5 最终验收 → 交付状态 → 结论 → 日志 → 轻量三件套（最后一项是「两周内能做完」的场景，前面整套可跳）。直接复制改。

## 一、分工表（P1）

```markdown
| 角色 | 负责什么 | 不做什么 | 交付物 |
|---|---|---|---|
| 用户 | 定范围、定验收标准、最终验收 | 不定实现细节、不中途改需求 | 验收结论 |
| 主理 | 全权执行、拆任务、写代码（单写者） | 不替用户改验收标准 | 成品 + 报告 |
| 子任务A | 只读分析，产出报告 | 不碰代码、不删文件 | docs/xxx.md |
| 子任务B | 独立复算，对账主流程数字 | 不复用主流程中间结果 | 对账表 |
```

四条硬规则：唯一负责人；写代码只有一个入口；子任务不共享中间文件；明确写出「不做」。

## 二、口径卡（P2）★ 最容易跳过、后果最重

签字后不得再改，改一次 = 重新开工。

```markdown
# 口径卡 · [项目名]

| 指标 | 算法（一句话可复算） | 样本范围 | 成本/成交假设 | 已知例外 |
|---|---|---|---|---|
| 例：5日收益 | T日收盘出信号，T+1收盘买入，持有5日 | YYYY-MM→YYYY-MM，N 只 | 单边 0.20% | 停牌跳空不剔除，单列 |

## 唯一引用源
- 数据：[路径]　版本/哈希：[…]
- 代码：[file:line]
- 哪个库/哪个模式：[strict]

## 禁止事项
- 不得用第二套口径交叉验证后只报好看的那套
- 不得在报告里同时出现两种口径的同一指标
- 不得用朴素 t 做结论行（表格可用作参考列）

签字：[用户]　日期：[…]
```

为什么必须签字：口径是唯一一处「改了没人看得出来」的地方。
实测代价：同一份数据落在两个库里、行数完全一致但数值有差，同一个 t 值会一个「显著」一个「不显著」，而报告里看不出任何异常。

## 四、最终验收清单（P5，人可判）

实测值填在这一行（通过线与例外见 `SKILL.md` 闸门表，不在此复制）：
`M1 推断步数=__ · M2 无结论=__ · M3 静默失败=__ · M4 一致性=__ · M5 歧义=__`

需求半边三问（用真实动作答）：真正要完成的任务 / 目前拿什么替代 / 我们的输出在他那一步怎么被用（要「先抄出去」就是没做完）。

## 六、轻量三件套（单用户 / 错了不掉钱 / 两周内能做完）

```markdown
# [项目] 一页纸
1. 失败判据：什么情况算白做（一个数）
2. 口径：每个要出的数，一句话写清怎么算（只许一个算法）
3. 边界：这次没覆盖什么
```

## 七、规划文档骨架（P1–P3 产物，七段）

```markdown
# [项目] 拆分与规划

## 0. 一句话判断现在的状态（信息展示器 / 决策器 / 半成品）
## 1. 已确认的事实（带数字与来源）
## 2. 任务拆分（阶段/交付物/验收标准/谁做）
## 3. 设计原则（写死，防跑偏）
## 4. 明确不做（范围外，写清为什么不做）
## 5. 风险与放弃条件
## 6. 两套验收标准的制定时间点（P3 初步 / P5 最终）
```

## 八、结论文档七件套（P6 产物）

缺前 6 项任一项 → 首页标「仅方法演练，不可引用」；第 7 项可选（`doctrine_check.py` 里 required=False）。

1. 数据口径（直接附口径卡）
2. 数字表（不是结论，是数字）
3. 判级理由：哪几条解释被数据排除了
4. 可信度速查：✅ 可信 / ⚠️ 打折 / ❌ 不得单独引用
5. 未覆盖的边界
6. 重算命令（每个数字一条）
7. 可引用的三条事实——读者只记三句，应该是哪三句
