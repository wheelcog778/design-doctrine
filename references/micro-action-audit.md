# 微动作审计（bug 检验 + 验收闸门）

> 把「用户从打开软件到做出决定」拆成逐个动作，逐动作记录他在推断什么、错了会掉多少钱。
> 它同时干两件事：**找 bug**（测试找不到的那类）和**卡验收**（M1–M5）。

## 一、为什么必须做

单元测试跑的是**代码路径**，微动作跑的是**人的路径**，两者不重叠。三类缺陷只在人的路径上暴露：

| 类型 | 真实例子 | 为什么测试发现不了 |
|---|---|---|
| 状态不一致 | 文档让用户去「配置目录」改持仓文件，程序只读 `~/.tool/portfolio.json` → 已持仓被当空仓，重复建仓 | 两个位置各自都能正常读写，单测全绿 |
| 信息缺口（含歧义输出） | 界面显示「通过 0」，既可能是没有合格标的，也可能是扫描故障 | 代码逻辑无错，信息不足以区分 |
| 责任转移 | 扫出 20 只候选，只有 2 个槽位，**软件不说选哪只** | 数据全对，缺的是「结论」不是「数据」 |

判断标准：**如果用户必须自己算一步，那一步就是缺陷位置。**

## 二、三步操作

### 第 1 步：冷启动实录

假装第一次用，从双击图标开始，**不跳步、不用已知快捷方式**，每个动作编号记四列：

| 列 | 记什么 |
|---|---|
| 动作 | 点了哪个控件 / 看了哪个区域 |
| 界面给了什么 | 具体字段与值，不写「显示了信息」 |
| 他必须推断什么 | 这一屏不能直接用、必须自己算/自己比的那一句 |
| 错了会怎样 | 概率 × 后果（金额级） |

真实案例前 8 步（选股工具，共 24 步）：

| # | 动作 | 界面给的信息 | 必须自己做的推断 | 出错后果 |
|---|---|---|---|---|
| 1 | 双击 exe | 3–5 秒白屏 | 卡死没有？要不要点「仍要运行」 | 低（误关=当天没跑） |
| 2 | 看顶部状态栏 | `未配置 Key` 琥珀色 | 没 Key 能不能用 | 中（以为必须配而弃用） |
| 3 | 填本金/模式/槽位 | 四个预填值 | 本金填总资产还是现金？现在该 A 还是 B | 高（本金口径错→手数全错） |
| 4 | 去配置目录改 JSON | 一个文件夹 | 12 个字段填什么？entry/stop 从哪抄 | 极高（路径本就是错的） |
| 5 | 看 11 个阈值 | 按模式预填的数字 | 要不要动？动了会不会破坏生存线 | 中（放宽即成批放行劣质票） |
| 6 | 点开始扫描 | 按钮变灰、无百分比 | 还要多久？现在到哪一步 | 中（只能滚日志猜） |
| 7 | 盯日志区 | 分类/圆桌逐只结论 | 数据源降级了，这次结论还能用吗 | 中（质量警告只在报告小字） |
| 8 | 切浏览器看报告 | 一堆表格 | 20 只里到底买哪只、买多少 | 高（无结论） |

### 第 2 步：三分类断点

- **信息缺口**：该显示的没显示，或显示了但分不清含义（现价 vs 计划价的偏离、总仓剩余额度、「通过 0」）
- **责任转移**：该给结论却给了原始数据（候选表、分散各处的条件）
- **状态不一致**：文档/界面/程序说的不是同一个东西（路径、字段、口径）

每条标「会不会导致真实亏损」，排序轴：**按「会不会导致用户下错单」降序**，不按好修程度。

**三分类 → M1–M5 对照**（同一件事的两个说法，别各叫各的）：

| 三分类 | 对应闸门 | 数法 |
|---|---|---|
| 责任转移 | M2 无结论动作 | 既不给动作也不给阻断理由的元素数 |
| 信息缺口 | M5 歧义输出 / M3 静默失败 | 一处显示对应两种以上含义 / 出错不告知 |
| 状态不一致 | M4 状态一致性 | 同一对象是否同一个 |

单人项目的交付线：单人 **M1 只能作前后对比**，因此按交付三档最多出「**带风险交付**」，
拿不到「验收通过」；残留项必须逐条写进状态卡。

### 第 3 步：回填 M1–M5

数一遍，不达线先修再谈新功能。

## 三、M1 数法协议（协议 v2，不可省略）

**一句话判定**：这一步的答案，**能不能从当前屏幕直接读出来**？

| 情形 | 计 |
|---|---|
| 一个字段/数字/状态图标直接给出答案 | 0 |
| 要心算、要翻别处、要两个值做比较、要领域知识做判断 | 1 |
| 同一行有多个独立推断 | 计**推断项**数，不按行数算 |

**M1 数的是推断项，不是行数。** 这一句就是算法——它消除了「同一步记 1 行还是拆 3 行」的粒度争议。

正例（计入）：
- 「本金填总资产还是现金」→ 要判断 → 1
- 「11 个阈值要不要动」→ 要判断后果 → 1
- 「20 只候选里买哪只」→ 要比较 → 1

反例（不计）：
- 「点开始扫描」→ 直接操作 → 0
- 「顶部显示未配置 Key」→ 只是读状态 → 0（若这一步要求他判断「没 Key 能不能用」，那个判断本身计 1，记在该行）
- 「按钮变灰」→ 只是读状态 → 0

**先判你有几个人能数**（v1 把「两人独立数」写成无条件硬约束，单人根本执行不了——做不到的 MUST 等于教人放过）：

| 情形 | 怎么做 | M1 能怎么用 |
|---|---|---|
| 两人独立数（首选） | 互不看第一份；报差值与分歧行；分歧 >2 取更严（数字大的） | 可作验收依据 |
| 只有一人（最常见） | 同一个人按同一协议数两遍，**隔开一段时间**、第二遍不看第一遍；报两遍的差值 | **只作改造前后对比**，不得单独作为「验收通过」的依据 |

写法（不写来源的裸数字不成立）：

- 双人：`M1=4（协议 v2，双人独立数，分歧 1 行：第 4 步）`
- 单人：`M1=3（协议 v2，单人两遍，第二遍差 1 行：第 8 步；只作前后对比）`

**三条硬约束**：
1. 协议版本必须写；改造前后必须同一版本，协议改了基线重数。
2. 分歧行必须写进表，不许只报一个数。
3. 单人的 M1 只能当趋势，不能当验收线——拿它当验收线，等于自己给自己发合格证。

> 为什么需要这一节：M1 是全文最核心的指标，而它原来只说「数非空的行数」——同一步两人能得到 6 和 9，
> 两者分居通过线两侧。花整章论证「一个数字只能有一个算法」，不能在最重要的指标上不执行。

### 非软件域的 M1 怎么数（同一把尺子，换个界面）

界面对**工具**来说是窗口，对**流程**来说是表单和群消息，对**文档**来说是目录和摘要。判定句不变：
**这一步的答案，能不能从当前这一屏直接读出来？**

| 界面形态 | 计 1（他要自己推断） | 计 0（直接可读） |
|---|---|---|
| 表单 / 纸质单 | 字段没写明填什么，得自己判口径（「金额」含税还是不含税） | 字段旁标了格式或示例 |
| 群消息 / 邮件 | 一段话里要自己算、自己比、自己排序 | 直接给出动作词（做/等/不做）和理由 |
| 文档 / 报告 | 要翻另一份文件或另一页才能对上结论 | 同一页给出结论 + 依据 + 出处 |
| 电话 / 口头流程 | 要记住上一位说的话才能做下一步 | 单子或系统上已显示上一步结果 |
| 审批流 | 要自己判断「这算不算超权限」 | 表单直接显示「需二级审批」 |

三条不变量：
1. 数的是「他必须自己完成的推断」，不是「信息量」——信息越多、要他自己挑，反而计得更多。
2. 界面换了，判定句不换；换成纸质单也要能数出同一个数。
3. 两个人各数一遍（或一个人隔开时间数两遍）并报分歧行，在非软件域一样适用：第二个人可以是不参与设计的同事，甚至是被服务的那个人。

## 四、闸门与数法

M1–M5 的指标名、通过线与例外只在 `SKILL.md` 闸门表有一份，本文件不复制（复制即两处漂移）。
这里只补两件本体没有的：域外适用说明与实测。

**这条通过线是在「非专家 + 任务导向 + 涉及钱」的工具上标定的**，不是常数。专家要控制权、不要被喂结论；
探索型工具的价值恰恰是给原始数据让人自己找。这两类先量一次现状当基线，改造后不高于基线即可。
M3/M4/M5 无例外——静默失败、状态不一致、歧义对专家也是缺陷。

实测对比（同一选股工具，M1 9→4、M3/M5 各余 1）只写在内部版案例的交付状态表里，
本文件不复制那组数字。

## 五、它是认知走查，不是用户测试

微动作审计本质是 **cognitive walkthrough（认知走查）**：一个专家按步骤扮演用户，逐屏问「他知不知道该干什么」。

**它能做到**：便宜、可重复、能在没有真实用户时找出「责任转移 / 歧义 / 状态不一致」三类结构缺陷。

**它做不到**：
- 发现不了「用户根本不会走到第 3 步」。走查假定他会往下走，真实用户不会。
- 给不出问题严重度的分布。多个真人能暴露的问题通常多于单人走查（**数量级未测量，标「未验证」**，别当数字引用）。

所以：**它是入场券，不是毕业证。** 有真实用户时，走查完再用 3–5 个人跑一遍同一张动作表；
没有真实用户时，在交付报告里写一句「M1–M5 来自单人走查，未做真人测试」。

## 六、四种误用

1. 当 UI 审美审。做的是「判断责任落在谁身上」，不是配色与间距。
2. 只看截图不动手。不走一遍真实动作，看不到「滑到底部才发现条件藏在灰字里」。
3. 只记功能不记推断。表里没有「他必须自己算」那一列，等于没做。
4. 把断点写成需求清单。断点要带「概率 × 后果」，否则无法排序，会先修好看的。

## 七、与其它闸门的关系

- bug 清单（代码层）：可一行命令复现 → 修了就是修了
- 微动作审计（人的层）：可一步动作复现 → 修了才算能给人用

两个都过再谈「成品」。只过代码层会发生什么：测试全绿，用户死于第 4 步。
