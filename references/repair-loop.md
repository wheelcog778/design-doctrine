# 修复循环：分析问题 → 定级 → 最小修复 → 双验收（软件与产品通用）

适用：手上有一批缺陷（用户报的、审计出来的、或自己跑出来的"数字不对"），要一次修完并交付。
**和入口 B 的关系**：入口 B 判"这东西还值不值得做"；本文件管"决定做之后，怎么把坏的地方修干净"。
产品优化也走这一套：改的是界面、默认值、文案、流程，验收方式换成可判读的检查（状态卡 gates 行）。

一句话主张：**没复现过的不许改；改了没测试的不算修好；测试通过但产物里看不见的，用户等于没得到。**

## 0. 先分层：这次修的是哪一类

| 类型 | 判据 | 典型 | 验收靠什么 |
|---|---|---|---|
| **静默错** | 界面上没有任何提示，但数字/动作是错的 | 用户填的参数被默认值覆盖、缓存 10 分钟当 10 秒用 | 定向测试 + 一条"能复现旧行为"的断言 |
| **静默失败** | 本该有结果，失败了却安静 | `except: pass`、只写日志不弹提示 | 用户界面/报告里能看到这条信息 |
| **误导输出** | 有数据、有提示，但读者会理解反 | 风险距离显示为负、同名不同版本 | 生成物 grep（值/版本号在产物里对不对） |
| **可复现事故** | 崩溃、卡死、必须绕过才能用 | 浮点异常、缺字段整份归零 | 复现脚本 + 回归测试 |

## 0.5 结构性缺陷：重建，不修补（同根因反复修补或跨模块改动时触发）

同一根因已打到第 3 次补丁，或改动跨 ≥3 个模块/文件组 → 停止叠补丁，按重建走：

1. **圈单元**：挑一个能被单独跑起来的接缝（一条命令、一个脚本、一个模块），先把它的输入输出与自检写死。
2. **列行为**：旧实现只用来列「必须保住的行为」清单，不照抄它的结构；新单元按目标行为从零写。
3. **对基线**：把旧树在该单元上的输出当基线，逐项比对，差异逐条解释（改对了 / 等价重构 / 漏了）。
4. **换一个跑一次**：新单元进树、旧单元出树，跑全量自检 + 该单元一次真实数据；失败就回退这一个单元，不带病往下铺。
5. **索引同步**：每完成一个单元更新产物索引与交接日志——做到哪、下一步、卡在哪。

**不要**：先把整棵新树搭好再一次性切换（切换当天无法定位是哪一块坏的）；也不要新旧两套并存超过一个单元（读者不知道该信哪个）。

## 1. 七步（顺序不可倒）

1. **复现**：写一条最小复现命令或 5 行脚本。跑不出旧行为，说明你修的不是这个 bug。
   复现要记录**原始输出**（不是"我推断它会这样"）。
   - **先选复现层**：用户报的是「界面/报告说 A、明细说 B」这类矛盾时，证据先到**生成物**里取——同一份报告/同一屏往往同时含结论行与逐项结论，矛盾是数据不是推测；看完生成物再回代码找「为什么两者不一致」，别从源码反推行为。
   - **桩掉贵的上游**（扫描、LLM、外部数据拉取、重型计算），只保留被测那一层，用生产者**真实的值域**逐个驱动：通过 / 条件通过 / 打回 / 未审 / 未知 各构造一次，打印动作与阻断项。值域大小通常 <10，一个循环就能判死「分得开 / 分不开」。
2. **定级**：按"会不会让用户做错决定"排，不按报错吓人程度排。
   会让用户做错决定/掉钱 → 致命；会让数字静默错 → 高；只影响排查 → 中；纯文案 → 低。
   同一天有十几条时，**先修"用户会因此动手"的那条**，不是先修看着最丑的。
3. **找根因，并找同类**：读调用链，不看报错文本。
   一条 `except: pass` 背后通常是同一个模式出现三处（拉取失败、计算失败、缓存失败）。
   修一处就等于没修——今天那条"拉取失败只写日志"在计算环节里也有一份。
4. **最小净复杂度修复**：改到症状消失为止，但**净复杂度必须下降或持平**。
   - 加一个判断/分支/字段/提示前，先找它顶替了哪个旧的；找不到顶替对象，就在报告里写一行「为什么不能合并」。
   - **补丁计数**（按同一根因算，不按报错文本算）：第 1 次 → 就地改；第 2 次 → 先把两处并成一个判断再改；
     第 3 次 → 判结构性缺陷，重写这一处，**不再叠补丁**。三次补丁的成本已经超过一次重写。
   - 不顺手重构**无关**代码：预算只给本次改动碰过的位置，不是大扫除的许可。
   - 在原位置留一行注释写清「原来是什么行为、为什么错」——改动越像重写，回归越难证明只修了这一个东西。
   - **改脚本文件本身时用整份写入或整行替换，别用带反斜杠的 heredoc 拼 Python**：`\n`、`\b`、`\U` 会被提前转义，
     源码里静默长出断行或退格字符（`\b` 变 0x08），只有 `py_compile` 才抳得住。写完先编一次再跑。
5. **定向测试先红后绿**：先写能复现旧行为的断言（红），再改到绿。
   一条测试对应一个缺陷编号；写不出测试的修复，在报告里标成"未验证"而不是"已修复"。
   **审别人的修复时先看 `git diff -- tests/`**：旧断言被改写是语义变更，处置见 SKILL.md 硬闸门「修既有测试的期望值」；新增测试只能证明新行为，不能证明旧行为该被改。
6. **回归三重**：
   - 全量测试（不是只跑新的）；
   - **跳过项不是通过**：时间门/环境门跳过的测试，用合成时钟或合成日历单独重跑并报 N/N；`skipped` 不能计成 pass；
   - 真跑一次（真实接口/真实数据，不是 mock）；
   - **生成物 grep**：版本号、那句结论、那个数字，在最终产物里出现过没有。
     代码里有不算——这是"静默交付"最常见的样子。
7. **收口**：版本号三处一致（界面/报告 meta/包名）→ 哈希进台账 → 残留登记 → 报告过 `doctrine_check.py`。→ **版图对账**：本次新增了条目/分支，写清它顶替了什么；答不出就退回第 4 步。

## 2. 什么不算修好（今天真实踩过的）

| 表面"修好"的样子 | 为什么不算 | 补什么 |
|---|---|---|
| 测试全绿 | 测试可能只测了函数，没测生成物 | 加一条"产物里能 grep 到"的检查 |
| 日志里有了 | 用户不看日志 | 提到控制台首屏与报告横幅 |
| 代码里改了默认值 | 已保存的用户状态会把它盖回去 | 区分"显式传入"与"缺省"，并写测试 |
| 修完没升版本号 | 下一个人分不清手上是哪版 | 改行为就升号并重打包 |
| 新旧数字两套并存 | 读者不知道该信哪个 | 只引用一个数，另附"旧数字/差异原因" |
| 同类问题第 3 次打补丁，单测全绿 | 每一处单点都对，整体长成一棵谁也说不清的判断树 | 停手合并：三处并成一条规则，重测后再交付 |
| 修复记录写着「已修」，后果没复测 | 一条后果可能由两个独立缺陷共同造成，补丁只改了相邻那个（另一个是值域不匹配或默认放行），声明的后果仍然成立 | 按**后果**验收，不按**改动**验收：把旧结论原样再跑一遍，看那句话还成不成立 |

## 3. 产品（非代码）怎么套

- **复现** = 找到用户会踩到的具体场景（哪一步、看到什么、接着会做什么）。
- **定级** = 这一步会不会让他做出错误决定；会 → 高。
- **最小修复** = 改默认值、改一句文案、加一个阻断、把一个隐含前提显式化；**不加新功能**。
- **定向测试** = 一条可判读的检查：状态卡里 `<!-- gates: M1=.. M2=.. -->` 那种能被脚本读的行，
  或一张"用户在 X 情况下会看到 Y"的对照表。
- **回归** = 让一个没参与改的人照着走路，不看你的说明。

## 4. 交付报告要写什么

和结论报告同一套七件套，但把"口径"换成"缺陷清单与复现命令"：
缺陷编号 / 原行为（含原始输出）/ 改法 / 测试名 / 判级 / 没覆盖什么。
末尾必须有一段 **"没做什么"**——真实边界比漂亮结论值钱。

## 5. 一个自检问题（交结论前问自己）

> 如果用户只做一件事——打开程序看一眼——他能看到我这次修的东西吗？
> 看不到，就还没修完。
